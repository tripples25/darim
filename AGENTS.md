# Darim: backend и отдельный frontend

Darim развивается как приложение из двух репозиториев:

- Этот репозиторий: https://github.com/tripples25/darim — ASP.NET Core API, бизнес-логика, авторизация, PostgreSQL, миграции и инфраструктура.
- https://github.com/sharphurt/darim-frontend — основной развиваемый интерфейс на React/Vite.

## Ветки и выкладка

1. Начинай работу от актуальной `dev`. Если работаешь в отдельной ветке, открывай PR в `dev`.
2. После попадания изменений в `dev` дождись выкладки на [тестовое окружение](https://test-ui.wishes.hype-ny.ru/) и передай пользователю ссылку и сценарий для проверки. Если задача затрагивает оба репозитория, передавай её на проверку после выкладки обеих частей.
3. Дождись явного подтверждения пользователя по результатам проверки. Только после него открывай релизный PR из `dev` этого же репозитория в `main`. Если после подтверждения в релиз добавились непроверенные изменения, верни релиз на проверку. Прямые пуши в `main` запрещены.

## Направление разработки

От Razor/Blazor-фронтенда отказываемся. Новые экраны и изменения пользовательского интерфейса реализуй в `darim-frontend`. `src/Wishlist.Client` — прежний Blazor-интерфейс, сохраняемый на время перехода. Не удаляй его и связанные серверные маршруты в рамках несвязанной задачи: завершение миграции требует отдельной проверки и задачи.

## Работа с двумя репозиториями

- Перед задачей, затрагивающей пользовательский сценарий, прочитай `AGENTS.md` второго репозитория и проверь соответствующие серверные контракты и React-код.
- Источник истины для API — серверные endpoints и `src/Wishlist.Contracts`. При изменении запросов, ответов, авторизации, CSRF или ошибок проверь потребителей в React и согласуй обе стороны.
- Не переноси бизнес-правила и защиту приватности только в интерфейс: сервер обязан обеспечивать их независимо от клиента.
- Найди checkout второго репозитория в доступном рабочем окружении. Не полагайся на фиксированный путь, в том числе при работе в worktree. Если checkout недоступен, явно сообщи об ограничении проверки. Не клонируй и не переключай чужие ветки автоматически.
- Это отдельные Git-репозитории: проверяй состояние каждого, делай отдельные коммиты и PR, указывай связанные изменения и порядок выкладки.
- Проверяй изменённую сторону её штатными проверками; для сквозного изменения проверяй обе. Явно сообщай, если вторую сторону или интеграцию проверить не удалось.

Локально сервер запускается по README на `http://127.0.0.1:5080`; Vite проксирует `/api` и `/auth` на этот адрес. Прокси разработки не гарантирует такую же маршрутизацию в production; настройки выкладки проверяй отдельно.

## Описания изменений для Telegram

Уведомления о выкладке формирует `ops/telegram-ci.sh` из заголовков коммитов (первой строки, `%s`), без тела сообщения и описания PR. Для API выводятся до трёх последних немержевых коммитов после предыдущей production-версии; если она неизвестна — только последний коммит. Поэтому каждый заголовок должен быть понятен сам по себе.

- Пиши заголовки коммитов по-русски: конкретное действие + затронутый сценарий + существенный результат. Ориентир — одна короткая строка до 100 символов, без потери смысла ради длины.
- Описывай итоговое поведение для пользователя или эксплуатации. Для исправления называй устранённый сбой и условие его возникновения; для инфраструктуры — что стало работать надёжнее или иначе.
- Не используй заголовки вроде `fix`, `update`, «Правки», «Доработки API» или только имя файла/номер задачи. Префиксы `fix:`/`feat:` допустимы, но после них должно идти содержательное описание.
- Технические детали, причину, проверки и ограничения раскрывай в теле коммита/PR. Существенный результат обязательно оставляй в первой строке: тело в Telegram не попадёт. Не включай секреты и персональные данные.
- При squash проверь итоговый заголовок коммита; если он берётся из заголовка PR, заранее сделай его информативным. При обычном merge проверяй заголовки отдельных коммитов: merge-коммиты исключены из списка API.
- Для задачи в двух репозиториях описывай вклад каждой стороны отдельно; в PR указывай связанную работу и порядок выкладки. Не обещай доступность всего сценария, если для неё ещё нужна выкладка второй стороны.

Примеры: `Исправлено бронирование желания при повторном запросе`; `Добавлен вход по одноразовому коду из Telegram`; `При сбое проверки здоровья сохраняется предыдущая версия API`.
