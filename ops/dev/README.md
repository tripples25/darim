# Тестовый контур Darim

Backend в Coolify: проект Darim, окружение staging, приложение darim-backend-test. Источник — ветка `dev`, Build Pack Docker Compose, файл `/compose.test.yaml`, режим Raw Compose. Контейнер не публикует порты. Caddy принимает тестовый домен и проксирует API, авторизацию и health через сеть darim-edge.

Перед созданием роли снимите резервную копию `wishlist` и проверьте текущие роли, использующие схему public. Скрипт `provision.sql` рассчитан на VPS, где `wishlist` является единственной существующей ролью приложения и бэкапа. Выполните его через psql от имени владельца БД в базе wishlist. Введите случайный пароль для darim_test. Внесите пароль и новый независимый ключ подписи в runtime-переменные Coolify `DARIM_TEST_DB_PASSWORD` и `DARIM_TEST_SIGNING_KEY`. Используйте значение пароля в hex, чтобы его можно было безопасно подставить в connection string. Таблицы и история EF создаются в `darim_test` при старте. Тестовый контур использует отдельный том ключей, а Telegram потребует отдельной конфигурации.

Установите `routes.caddy` как отдельную динамическую конфигурацию после проверки обоих upstream. Во frontend Coolify используйте alias `darim-test-ui` и пустое поле домена, чтобы Caddy не получил два маршрута для одного host.

Оба репозитория используют существующие вебхуки GitHub в Woodpecker. У расширения конфигурации `ci-config.py` свои правила для репозиториев 1 и 2. Push в dev получает фиксированный `deploy-dev.yaml` без клонирования кода. Этот шаг подписывает запрос в Coolify отдельным секретом приложения `coolify_dev_webhook_secret`, доступным на событии push. Push в main и ручная проверка main используют файл из соответствующего коммита. Конфигурация для остальных событий не запускает сборку. Параметр Send netrc credentials отключён. Расширение устанавливается из доверенного checkout администратором VPS.

После push в dev сверьте SHA обоих приложений в Deployment Logs Coolify, проверьте `/frontend-release.json`, `/frontend-health`, `/health` и `/api/auth-info` на тестовом домене. Для main нужен активный GitHub ruleset с обязательным PR и без прямого push через bypass. На production пользуемся штатным Woodpecker и проверкой версии на основном домене.
