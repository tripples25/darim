# Тесты, сборка и деплой

Этот вариант GitHub Actions отключён. Активная система —
[Woodpecker CI](woodpecker.md).

## Схема

GitHub Actions запускает .NET-тесты (включая PostgreSQL в Testcontainers),
проверки ops-скриптов, release-publish и Playwright на push и pull request.
После успешных тестов собирается Linux amd64 Docker-образ. На main образ
сохраняется вместе с Compose и ops в артефакт `deployment-<commit SHA>` на 7 дней.
Код чужих PR не получает секретов production.

Для деплоя: Actions → CI/CD → Run workflow → ветка main → Deploy to production.
Этот запуск заново проверяет коммит, собирает образ и только затем развёртывает его.
Деплой другой ветки запрещён. Окружение production ограничено веткой main.
Запуски production выполняются последовательно; миграции автоматически не откатываются.

## Подготовка сервера

Нужен Linux x86_64 с Docker Engine, Compose v2, curl и доступом в интернет.
DNS домена должен указывать на сервер, порты 80/443 открыты.
Создайте пользователя деплоя с SSH-ключом и доступом к Docker (это высокие права).
Создайте доступный ему каталог, например `/opt/darim`, и поместите туда
заполненный `.env` из `.env.example`, права 600. Секреты приложения остаются
на сервере и не передаются в GitHub. Настройте Telegram до первого деплоя.

В Settings → Environments → production добавьте:

| Тип | Имя | Значение |
| --- | --- | --- |
| Variable | DEPLOY_HOST | IP или DNS SSH-сервера |
| Variable | DEPLOY_USER | SSH-пользователь |
| Variable | DEPLOY_PORT | SSH-порт, по умолчанию 22 |
| Variable | DEPLOY_PATH | Абсолютный путь, например /opt/darim; без пробелов |
| Variable | DEPLOY_HEALTH_URL | https://ваш-домен/health |
| Secret | DEPLOY_SSH_KEY | Приватный SSH-ключ выделенного пользователя |
| Secret | DEPLOY_KNOWN_HOSTS | Проверенный known_hosts сервера |

Fingerprint SSH-сервера проверьте через консоль провайдера перед добавлением
known_hosts. Не отключайте StrictHostKeyChecking. При желании включите
Required reviewers для production. Доступ к изменению main и workflow должен
оставаться только у доверенных участников.

## Что делает деплой

Проверяет настройки, передаёт архив по SSH в `releases/<SHA>-<run ID>`,
проверяет SHA256, загружает готовый образ, поднимает БД и применяет миграции.
При существующем приложении сначала выполняет S3-бэкап: его настройки из
README обязательны для обновлений. Затем обновляет app/Caddy и проверяет
публичный HTTPS /health. Успех записывается в `current-release`.
Compose использует фиксированное имя проекта darim, чтобы сохранялись volumes.
Нельзя одновременно запускать ручной deploy.sh и деплой из Actions.

Если проверка здоровья не прошла, job завершается ошибкой. Автоматического
отката нет: миграции могут быть несовместимы с предыдущим кодом. Предыдущие
образы и каталоги releases сохраняются для ручного восстановления.
Для отката совместимой схемы укажите предыдущий DARIM_IMAGE и Compose-файл
предыдущего релиза; для несовместимой схемы потребуется восстановление БД.
Следите за свободным диском и удаляйте старые релизы/образы после проверки бэкапов.

Без серверных настроек тесты и сборка работают, а запрошенный деплой завершается
понятной ошибкой до подключения к серверу. Реальный деплой требует отдельной
проверки после подготовки VPS.
